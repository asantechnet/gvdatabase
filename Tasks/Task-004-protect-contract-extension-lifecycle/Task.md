# Task Task-004 — Protect the contract extension lifecycle

## Objective
Make employment and other contract extensions keep their origin and enforce one coherent extension lifecycle: editing cannot erase the parent, a parent cannot have two live extensions, the parties must match, and no new orphan extension can be written. Contract edit-window behavior must also follow the approved Task-001 policy.

## Context and problem
The audits confirmed two high-severity defects and two missing guards. `ContractForm.vue` always sends `parent_contract_id: null` in edit mode, and `ContractController::update` persists it while rebuilding `snapshot_data`, so a routine edit silently destroys the extension origin. The controller also takes scalar ids, so the global edit-window middleware cannot see a bound contract. `extensionParent()` checks role, cancellation and status but not an existing live extension or whether the extension's employee/applicant matches the parent. Existing orphan extension rows 21, 23 and 25 prove the invariant is unenforced. `EXT-20261110-001` is the same parent-loss defect as `CE-001`.

## Scope
### Included
- Preserve `parent_contract_id` and `snapshot_data.extension_of` when an extension draft is edited.
- Prevent an edit from changing or clearing the parent; only creation may establish it.
- Bind or explicitly resolve the contract on update/cancel/service-update paths so the approved edit-window policy can evaluate it.
- Guard extension creation against a second live extension of the same parent, using the existing renewal error vocabulary.
- Require the extension's employee/applicant party to match the parent, with a clear validation error and no row written on mismatch.
- Enforce the extension-with-parent invariant for new writes; audit existing orphans without guessing their parent.
- Hide Extend when a live extension already exists, and keep the form's parent value out of update payloads.
- Add regression tests for edit preservation, duplicate renewal, party mismatch, orphan prevention, and the approved window branch.

### Excluded
- Built-in service extensions generated by `ContractGenerationService`; Task-006 owns that file and its assignment behavior.
- The shared "View full details" action; Task-005 owns it.
- Academy commission enrollment; Task-009 owns it.
- Changing the general contract status model, document templates, or print layouts beyond preserving the existing extension snapshot key.

## Preconditions and assumptions
- Task-001 has approved whether contract edits are governed by the one-hour window.
- `parent_contract_id` and `snapshot_data.extension_of` are the canonical extension-origin fields.
- Existing orphan rows must not be auto-attached to a guessed parent; manual data repair is safer than inventing a relationship.
- Employment and other contracts are the target; built-in service contracts keep their existing generator until a separate task changes it.

## Dependencies
- `Task-001` — requires the approved edit-window policy for the `EW-003` branch.

## Contracts and boundaries
- API contract: `parent_contract_id` is create-only for extensions; update requests cannot reparent a record.
- Snapshot contract: `snapshot_data.extension_of` survives every draft edit and names the parent contract number.
- Error contract: invalid extension creation keeps `422 business.contract_extension_invalid`; duplicate live renewal uses `business.contract_renewal_exists` or an equivalent existing translated code; party mismatch uses a new translated code only if no suitable existing code exists.
- Permission/data-scope contract: only a holder who can manage the parent may create its extension; the parent and child remain in the same contract category.
- Invariant: a row with `contract_role = extension` has a non-null parent; a primary has no parent.
- Files/modules this task must not modify: `app/Services/Contracts/ContractGenerationService.php`, `routes/api.php`, `app/Support/EditWindow.php`, employee/staff screens, Academy commission screens.

## Exclusive file ownership

- `app/Models/Contract.php` — extension predicates and invariant hooks.
- `app/Http/Resources/ContractResource.php` — expose editability and preserve origin fields.

## Acceptance criteria
- [ ] Given a draft extension, when it is opened in Edit contract and saved without changes, then parent_contract_id and snapshot_data.extension_of remain unchanged.
- [ ] Given an edit request that supplies a different parent_contract_id, when it is submitted, then the request is rejected or the field is ignored so the extension cannot be re-parented.
- [ ] Given a primary contract with a live extension, when another extension is requested, then creation is rejected with the existing business.contract_renewal_exists error.
- [ ] Given a parent and an extension with a different employee or applicant, when creation is requested, then it is rejected and no extension row is written.
- [ ] Given a new extension, when it is created through the API or UI, then it has a parent and satisfies the invariant; existing orphan rows are reported for manual repair rather than guessed.
- [ ] Given the approved edit-window policy, when a contract edit is expired, then the API and UI follow that policy exactly and enforce the override audit when applicable.
- [ ] Given the shared contract register, when a parent already has a live extension, then Extend contract is unavailable and the form sends parent_contract_id only during creation.

## Verification plan
- Automated checks: `php artisan test tests/Feature/ContractExtensionTest.php tests/Feature/ContractEditWindowTest.php`; `npm run typecheck`.
- Migration check: run the migration in the test database, confirm a second run/rollback is safe, and confirm existing orphans are reported without being silently reassigned.
- Manual/UI scenarios: employment and other contract registers; create an extension, edit and save it unchanged, verify the origin remains; attempt a second extension; attempt mismatched parties.
- Expected result: parent origin survives, duplicate and mismatched-party attempts fail visibly, Extend is hidden for live renewals, and the chosen window branch is enforced.
- Regression: existing contract list print/cancel/delete behavior and contract access scopes remain unchanged.
- Required evidence: test output, migration output, before/after API JSON for an extension edit, and row-menu observations from both registers.

## Implementation notes
- Prefer dropping `parent_contract_id` from the update payload entirely, then reject or ignore it server-side as defense in depth.
- When rebuilding a snapshot, merge the existing `extension_of` key for extension rows rather than replacing the origin metadata.
- Treat "live" consistently with the existing status rules; do not introduce a new status vocabulary without updating the contract register and tests.
- If a legacy orphan cannot be repaired safely, leave it untouched, surface it in a documented audit query, and prevent new orphans.
- Keep the contract window branch behind the Task-001 decision; do not enforce a rule the product owner has not approved.

## Risks and rollback
- Risk: an over-broad invariant migration could fail on the three known orphans; make the migration idempotent and non-destructive.
- Risk: duplicate-renewal checks can race; lock the parent row during creation and test the competing request path where practical.
- Risk: party matching may be intentionally loose for organizational Other contracts; the task must state the chosen rule for null parties rather than guessing.
- Rollback: revert the controller/form/migration changes and restore the previous snapshot behavior; existing parent links must not be deleted by rollback.

## Handoff checklist

- [ ] Existing orphans are documented, not silently repaired.
- [ ] The approved contract window branch is tested.
