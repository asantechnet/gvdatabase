# Educational firm simplification — system-wide restructure

**Status:** implementation and Phase G verification complete; manual print acceptance and environment-limited build/preview remain open — updated 2026-10-08
**Scope:** contracts, visitors, leads, services, incomes, expenses, loans, invoices, companies, tasks, applicants, educational master data.
**Extends / supersedes:** `customer-applicant-merge.md`, `service-contract-linkage-plan.md`, `PACKAGES_AS_SERVICES_PLAN.md` (their service/package layer is retired by §4–§5 here).
**Bonus (separate file):** `contract-as-case-plan.md`.
**Environment:** not in production. No backward compatibility, compatibility aliases, invoice archival or historical invoice preservation. Retired entities are removed from fresh schemas and dropped from existing schemas; cleanup migrations do not reconstruct them.
**Latest user decision (2026-10-08):** remove invoices, counterparty companies, commissions and outsourcing completely, superseding the earlier historical-receipt instruction. No receipt-retention guard or archival flow remains. The firm\'s own branding and document headers remain.

## 2. Locked decisions (confirmed with the product owner)

1. **Applicant storage** — *one shared identity row + three per-service detail tables.* `applicants` keeps identity/contact/portal/marketer/employee/stage. Three new tables hold the differing data 1:1: `scholarship_applicant_details`, `test_applicant_details`, `academy_applicant_details`. Nothing becomes polymorphic: contracts, tasks, incomes, expenses, attachments and reports keep a single `applicant_id`.
2. **Applicant ↔ contract pivot** — rename `contract_service` → **`applicant_contract`**, *keeping its necessary columns* and dropping the rest (§3.4).
3. **Payment state** — `payment_status` / `amount_paid` are **computed from linked income receipts**, but **overridable by users holding the finance permission** (`override_contract_payments`).
4. **Contract pages** — **three dedicated pages**, one per built-in service, each with its own list and its own create form. Employment and other contracts keep their existing pages.
5. **Income entry** — **one income receipt row per selected service line**.
6. **Execution** — implement end to end, recording progress in this file.

### Decisions I made (documented, flag if wrong)

| Question | Decision | Why |
|---|---|---|
| `outsourcing_company_id` / `outsourcing_percentage` on contract lines | Retired together with `Company`. `OutsourcingAccrual`, `OutsourcingSettlement`, `OutsourcingController`, `OutsourcingAccrualService`, `/outsourcing/*` routes, the outsourcing nav and settlements UI are removed. Any real outsourced cost is recorded as an expense with an optional applicant. | A settlement has no counterparty once companies are gone. |
| Commission and outsourcing ledgers as a whole | Removed entirely on the product owner's instruction ("rip these concepts out … like they never existed"). Employee commission rates, delivery/settlement machinery, the `/commissions*` and `/outsourcing/*` routes, permissions, reports, dashboards, audit entries, employee `employment_type` and every related UI string are deleted. Incomes remain the only payment record. | The firm pays staff through salaries and tracks supplier cost as ordinary expenses; the ledger added accounting complexity the product no longer wants. |
| `contracts.counterparty_company` (plain string) | Kept as optional free text. Nothing selects a company row. | It is a printed document field, not an entity. |
| `Setting` company profile / branding (`CompanyProfile`, `useBranding`, letterheads) | **Kept.** "Company" here means *our own firm*, not the removed counterparty entity. | Removing it would break every printed document. |
| `applicant_universities` (multi-application tracking) | Kept, but only for `service = scholarship` applicants. | Scholarships are the only built-in service with universities. |
| Applicant stages / pipeline | Kept in this plan; **moved to the contract as the case** by the bonus plan. | Bonus task governs. |
| Loans / pending transactions | Kept unchanged apart from the applicant link (already optional) and the removal of company/invoice references. | Not in scope for removal. |
| Favorite subjects / skills / teachers | Stored as real pivot tables (`scholarship_applicant_subject`, `test_applicant_skill`, `academy_applicant_teacher`) rather than JSON. | Matches house style (`package_service`, `contract_service_employee`, `applicant_universities`) and keeps reporting/validation honest. |

## 3. Target domain model

### 3.1 Built-in services

```php
// app/Support/BuiltInService.php
const SCHOLARSHIP = 'scholarship';
const TEST_OFFER  = 'test_offer';
const ACADEMY     = 'academy';
```

* `ALL = [scholarship, test_offer, academy]`, `labels()` for UI/i18n keys, `contractTypes()`.
* Used as the enum value for `contracts.service`, `applicant_contract.service`, `contract_templates.service`, and `applicants.service`.
* There is no `services` table and no service CRUD.

### 3.2 Applicants

`applicants` (existing table, trimmed):
* Keeps: identity (`name`, `father_name`, `father_phone`, `contact`, `email`, `address`, `tax_number`), attribution (`marketer`, `marketer_id`, `responsible_employee_id`), portal (`user_id`), workflow (`current_stage_id`, `status`, `notes`, `profile_data`, `profile_completed_at`), soft delete + audit.
* Adds: `service` (enum, not null, indexed).
* Drops: `country_id`, `university_id`, `education_level_id`, `percentage`, `language_id`, `semester_id`, `application_date`, `date`. Retain `parent_applicant_id` until applicant grouping is revisited, as recorded in the progress log.
* Relation: `details()` — one of the three detail models chosen by `service`.

### 3.3 Per-service detail tables

`scholarship_applicant_details` — `applicant_id` (unique FK), `passport_id`, `grade_score` (decimal), `country_id`, `contract_type_id`, `education_level_id`, `semester_id`, `university_id`, `university_fee` (decimal), `notes` + pivot `scholarship_applicant_subject(subject_id)`.

`test_applicant_details` — `applicant_id` (unique FK), `passport_id`, `test_id`, `notes` + pivot `test_applicant_skill(skill_id)`.

`academy_applicant_details` — `applicant_id` (unique FK), `father_name`, `program_id`, `time_id`, `duration_id`, `notes` + pivot `academy_applicant_teacher(teacher_id)`.

Money is **not** stored here. The form collects `service_fee` / `fee`, `currency_id`, `currency_rate`, `discount` and writes them to `applicant_contract`. `university_fee` stays on the scholarship detail because it is a reference cost, not the firm's price.

### 3.4 `applicant_contract` (renamed from `contract_service`)

Kept columns: `id`, `contract_id`, `applicant_id`, `fee`, `currency_id`, `sold_by_employee_id`, `marketer_id`, `notes`, `timestamps`, `deleted_at`.
Added columns: `service` (enum), `currency_rate` (decimal 15,8), `discount` (decimal 20,6, default 0), `amount_paid` (decimal 20,6, default 0), `payment_status` (enum `paid|unpaid|partially_paid`, default `unpaid`), `payment_status_overridden` (bool), `amount_paid_overridden` (bool).
Dropped columns: `service_id`, `service_variant_id`, `customer_package_id`, `outsourcing_company_id`, `outsourcing_percentage`, `country_id`, `education_level_id`, `language_id`.
Retired aux table: `contract_service_employee` / `applicant_contract_employee`; commission and delivery-share concepts are removed.

`payment_status` is derived by `ApplicantContractPaymentService`:

```
paid    ⇔ amount_paid >= fee - discount
partial ⇔ 0 < amount_paid < fee - discount
unpaid  ⇔ amount_paid = 0
```

`amount_paid` = sum of `incomes.amount` (converted at the stored receipt rate) for that line, unless `amount_paid_overridden`. Recalculation is triggered on income create/update/delete and on fee/currency/discount change.

### 3.5 Contracts

* Add `service` (enum, nullable — null for employment/other contracts).
* Drop `source_service_id`, `company_id`.
* Keep `contract_role`, `parent_contract_id` (repeat sale of the same built-in service to the same applicant stays an **extension**), `contract_template_version_id`, `snapshot_data`, counterparty fields, cancellation fields.
* Relation: `applicantContracts()` (`hasMany ApplicantContract`).

### 3.6 Contract templates

* Add `service` (enum, nullable). A template with `service` set is one of the three built-in service templates and is **editable** from the contract-documents page.
* Drop `service_id`, `package_id` (both entities removed). Keep `position_id` for employment templates and the contract-type/version/artwork machinery untouched.

### 3.7 Finance

* `incomes`: add `applicant_contract_id` (nullable FK). Drop `invoice_id`, `invoice_amount`, `company_id`. Keep `applicant_id` (optional), `visitor_id`, `employee_id`, `receipt_number`, rate/base columns.
* `expenses`: drop `company_id`. Keep optional `applicant_id`.
* `IncomeReceiptService`: a linked payment prints one built-in service line, its frozen fee/discount and payment balance, applicant identity and receipt number. Standalone incomes remain valid. There is no invoice receipt branch, archive format, invoice linkage or retention guard.
* **Commission and outsourcing ledgers removed (user-confirmed 2026-10-08).** `CommissionAccrualService`, `OutsourcingAccrualService`, `CommissionAccrual`, `CommissionSettlement`, `OutsourcingAccrual`, `OutsourcingSettlement`, `CommissionController`, `OutsourcingController`, their resources, the `/commissions*`, `/commission-settlements*` and `/outsourcing/*` routes, the per-service employee commission rates (`employee_service_commissions`), the delivery-recipient and invoice commission-recipient pivots, the commission/outsourcing snapshot columns on `invoice_service`, the supplier share (`outsourcing_company_id` / `outsourcing_percentage`) and commission rate (`marketer_percentage`) on contract lines, and the salaried/commission split (`employees.employment_type`) are all deleted, together with their permissions, audit entries, reports, dashboards, translations and UI. Incomes remain the single payment record. No backward compatibility, no data migration.

### 3.8 Tasks

* `tasks` gains `applicant_contract_id` (nullable FK, indexed).
* New `ContractTaskService::ensureForApplicantContract(ApplicantContract $line, ?User $actor)` creates one task per line:
  * board: deterministic `firstOrCreate(['title' => 'Contracts'])`,
  * title: `Deliver {service label} — {applicant name}`,
  * description: applicant, service, contract number, fee/currency, payment status,
  * `applicant_id` + `applicant_contract_id` set,
  * assignee: `applicant.responsible_employee.user_id` else the actor,
  * idempotent: skipped when an open task already exists for that `applicant_contract_id`.
* Called from the contract creation path (the one place all three contract pages go through), inside the same transaction as the `applicant_contract` insert.

### 3.9 Educational catalogs (AC15)

New tables/models, all following the `Semester`/`EducationLevel` shape (`name`, `sort_order`, `is_active`, soft deletes, auditable):

| Catalog | Table | Extra columns | Used by |
|---|---|---|---|
| Subjects | `subjects` | — | Scholarship favourite subjects |
| Tests | `tests` | `description` | Test Offer test |
| Skills | `skills` | — | Test Offer skills |
| Times | `times` | `description` | Academy time |
| Teachers | `teachers` | `contact`, `email` | Academy teachers |
| Programs | `programs` | `description` | Academy program |
| Durations | `durations` | — | Academy duration |
