## Objective
Universities and countries have a relationship surface with notes and interaction history, reachable from Educational Data and from a visa case. The visa case is deliberately constrained: it may contact only its selected country and the universities already attached to that case, and it displays only relationship interactions linked to that case. Educational Data remains the global catalogue view. The per-service case workspace also renders every structured field of the contract behind its line without exposing sibling service lines. The applicant case page keeps the plural responsible-employees control that Task-046 moves forward.

## Context and problem
`CrmRelationshipDetails.vue` and `crmRelationships.ts` are hard-wired to `visitor | applicant`; `CrmInteractionController` maps only those two models, and the existing `/crm/{type}/{id}` routes constrain those types. Countries and universities already carry phone, email, portal URL and (for universities) city, website and description, but they have no notes column and no `interactions()` relation. Educational Data has no relationship or row-level quick-contact action.

On the visa case page, the selected country comes from the applicant's service detail and attached universities come from `applicant.universities`; the page already renders those rows. However, its phone/email quick contacts cannot record a university/country interaction, and it has no relationship overview. Critically, `crm_interactions` has no applicant/case link. Filtering by university/country alone would show another case's history for the same university, so the case needs a nullable `applicant_id` association and a case-scoped read/write contract. The visitor follow-up list demonstrates the expected quick-contact pattern: `ContactActionMenu` on the phone/email cell, with `contactableType`/`contactableId` so a completed contact becomes a CRM interaction.

Separately, the service case's `ApplicantContractResource` exposes only `contract_number`, `status`, `contract_role`, `parent_contract_number` and `is_extension`; `service-case.vue` therefore shows a contract chip but not the contract's dates, parties, signatory, template/version, country/language, cancellation state or payment context. `ContractResource` already owns the complete contract representation. The case must consume it without exposing sibling service lines or applying contract edits from the case.

File ownership has to move before this work starts. Task-046 owns `applicant-case.vue` for plural responsibility and Task-028 owns `ApplicantContractResource`, `service-case.vue` and `serviceCases.ts`; this task takes those forward because it is the only remaining writer. Task-038 owns `routes/api.php`, so this task adds a separate `routes/crm.php` and Task-038 adds the guarded include seam. Task-035 owns `educational-master-data.vue` for its audit rail; this task adds the relationship/quick-contact controls only after that page change.

## Contracts and boundaries
- Schema: `countries.notes` and `universities.notes` are nullable text fields. `crm_interactions.applicant_id` is nullable, indexed with `contactable_type`/`contactable_id`, and foreign-keyed to `applicants` with `nullOnDelete`. `applicant_id = null` means a global Educational Data interaction; a positive value means a visa-case interaction.
- Global relationship read: `GET /api/crm-relationships/{type}/{id}` accepts only `university|country`, requires `view_university`/`view_country`, and returns the type profile, global notes and all interactions for that record.
- Case relationship read: `GET /api/crm-relationships/{type}/{id}?applicant_id={applicant}` requires `view_applicants` plus the existing applicant/case view scope. The target must be the applicant's selected country or an attached university; otherwise 403/422 with no data. The response omits global notes and returns only interactions whose `applicant_id` matches.
- Case relationship aggregate: `GET /api/applicants/{applicant}/relationships` requires the same case view scope and returns `{applicant_id, country, universities, records}`. `country` is the selected country or null; `universities` contains only `applicant_universities` rows with their university profile; `records` is a newest-first flatten of the applicant's linked interactions with `id`, `target_type`, `target_id`, `target_name`, `channel`, `title`, `notes`, `contacted_at`, `follow_up_at` and `creator`. No global notes, unrelated universities/countries or other applicants' records are returned.
- Global write contract: `PATCH /api/crm-relationships/{type}/{id}/notes` and interaction create/update/delete without an applicant context require `edit_university`/`edit_country`. `POST /api/crm-relationships/{type}/{id}/interactions` accepts the existing interaction payload; an optional `applicant_id` switches to case semantics.
- Case write contract: creating or mutating an interaction with `applicant_id` requires the existing case-edit permission and manage scope. The target must be attached to that applicant at request time; an unattached target returns 422 `business.relationship_not_linked_to_case` and writes nothing. The interaction stores the applicant id; `applicant_id` is immutable on update, and a case-linked interaction cannot be moved to another applicant. A case-linked interaction update/delete requires case manage scope; a global interaction continues to require master-data edit permission.
- Notes compatibility: global profile notes remain on the country/university and are edited only through the global relationship context. They are not case-specific and are neither displayed nor mutated from a visa case. A case note is an interaction with channel `note` and the applicant id.
- Quick contact: use the existing `ContactActionMenu` for phone/email. In Educational Data pass `contactableType`/`contactableId` only with `edit_university`/`edit_country`. On the visa case pass them plus `caseApplicantId` only when the caller can edit the case; otherwise the call/email action still opens but no interaction is written. Do not invent WhatsApp audience/template options for university/country.
- Visa case behavior: the selected country is the only country contact/relationship target; attached `applicant.universities` rows are the only university targets. Do not add a catalogue picker or arbitrary ID lookup. Removing a university/attachment removes its case contact/record entry; existing interactions remain stored but are not returned until the target is linked again.
- Case record display: the applicant case page renders a dedicated records card only from the aggregate endpoint. It shows target name/type, channel, title, notes, contacted date and creator; no global notes, no other applicant's records, and an empty state when none exist. It must not call the global relationship endpoint for a catalogue list.
- Popup behavior: `CrmRelationshipDetails` accepts `caseApplicantId` and uses the case read/write contract when present. Existing applicant/visitor callers and the global university/country callers from Educational Data are unchanged. In case context, hide the global notes editor and the existing `readonly` controls behave as described.
- Service-case payload: `GET /api/applicant-contracts/{line}` returns the existing line fields plus `contract: ContractResource` when the parent contract is loaded. The resource is read-only; no contract write endpoint is added. The nested contract must not include `services` (no `applicantContracts` eager load), `applicant` or employee payloads unless already loaded by the controller; add a focused assertion that sibling lines are absent.
- Service-case UI: the contract section renders every structured contract field, uses existing locale keys, formats dates/money with the shared formatters, shows explicit unavailable text for null values, and keeps the existing stage, history, tasks and finance sections. Contract content and snapshot are not rendered as raw JSON; if a document link is already available, it must retain the existing print behavior and page size.
- Compatibility: existing `GET/PATCH/POST /api/crm/{visitor|applicant}/...` routes, applicant/visitor payloads and popup controls are unchanged. The only additive endpoint families are `/api/crm-relationships/` and `/api/applicants/{applicant}/relationships`. No `@page` rule or global print selector is added.
- Shared UI handoff: Task-035 is the exclusive owner of `resources/ts/pages/educational-master-data.vue` for the audit rail. This task adds only the country/university relationship action and quick-contact controls after that change; it must preserve the audit rail, columns, filters, edit/delete actions and print behavior and must not create a second table or fetch path.

## Implementation notes
Add the two `notes` columns and `crm_interactions.applicant_id` in separate additive migrations; do not add a new interactions table. `CrmInteraction` already stores a polymorphic `contactable_type`/`contactable_id`; add `applicant_id` to its fillable fields, the applicant relation and the resource. Existing rows must stay global with a null applicant id. Add a `MorphMany` relation on `Country` and `University` for their interactions.

Resolve a relationship through one controller helper that maps `university` and `country` to their models and returns 404 for any other type. Keep the old `updateNotes()`/`store()` paths working for `visitor` and `applicant`; use the same methods from `routes/crm.php` or small wrappers so validation and interaction shape stay identical. Extend `authorizeInteractionMutation()` with the two new morph classes and make `authorizeMutation()` an explicit four-way map; never fall back to `edit_visitors` for an unknown type.

Add case resolution in `CrmInteractionController`: read the applicant's selected country through `detailRelationName()`/`detail()` and attached universities through `universities()`. A target is linked only when the country id matches the service-detail country or the university id is in `applicant_universities`. A case-scoped read returns only `where('applicant_id', $applicant->id)` interactions and omits global notes. ## Risks and rollback
- Risk: a case displays another case's relationship history for the same university. Mitigation: the applicant_id link, case-scoped read, cross-case fixture and aggregate assertions. Never filter by contactable alone for a case.
- Risk: global notes leak into a visa case. Mitigation: omit them from the case resource and never render the global notes editor in case context; test with different global notes on each record.
- Risk: case-scoped writes become a backdoor to master-data edits. Mitigation: only interaction rows are writable; notes and contact fields remain master-data-edit-only; validate the target is already linked.
- Risk: existing interactions have no applicant id and appear missing from case pages. This is intentional: there is no reliable case association to backfill. Record the legacy/global-only limitation and do not guess.

Mitigation: one parent contract per line, no `applicantContracts` eager load, and a payload-size/response test; if the response becomes unacceptable, introduce a read-only contract summary resource with the same structured fields rather than dropping data from the frontend.
